# 新增 Agent 适配指南

适用于新增 Agent，也适用于现有 Agent 的新协议、新用途和归属规则。依据当前 Antigravity、Codex 实现与已确认的产品规则整理，核对日期：2026-10-22。本文是开发检查指南，不代表文中的能力已经对所有 Agent 实现。

适配的交付目标是：请求能被正确采集、解释、归入会话和轮次，展示与统计一致，并且规则升级后可以用本应用保存的证据重算。仅能显示模型回复，或增加一个 Agent 图标，不等于适配完成。

## 1. 先区分五件事

| 问题 | 要确定的内容 | 不能互相替代的依据 |
| --- | --- | --- |
| 谁发出的 | Agent 身份与适配器选择 | 使用同一模型、服务商或域名，不代表同一 Agent |
| 请求做什么 | 正常生成、标题生成、搜索、输入检测、预热、后台任务、连接事件等 | 用途不等于会话归属；失败状态不等于用途 |
| 属于哪个会话 | 原生会话标识与标识的作用域 | 工作区、目录、连接、用户名、提示词相同，不代表同一会话 |
| 在哪一轮 | 原生轮次标识或明确用户输入边界，以及产品分组规则 | 一次请求、一条回复、一次工具调用都不必然是一个新轮次 |
| 与谁关联 | 父子会话、工具调用与独立模型请求之间的关系 | “像子 Agent”或内容相关，不足以建立父子关系 |

Agent 身份、协议格式和传输方式也应分别处理。一个 Agent 可以使用多个 Provider 或 HTTP/WS；一个 Provider 也可以被多个 Agent 使用。

## 2. 研究阶段：把推断变成可核对的规则

先按[需求模板](requirements/TEMPLATE.md)记录范围和验收，不直接从样例写判断分支。允许大胆提出假设，但进入代码前须明确证据、反例和适用范围。

每一条规则至少填写以下内容：

| 记录项 | 应写清楚什么 |
| --- | --- |
| 结论 | 判断的是身份、用途、轮次、关联、协议还是用量 |
| 字段路径和作用域 | 精确路径、类型、合法值；属于单次 HTTP 请求、WS 当前帧、握手连接还是历史消息 |
| 逻辑 | AND/OR、冲突处理、缺失处理、是否依赖报文完整性；避免“应该是”“看起来像” |
| 证据来源 | 实际样本定位；官方文档或源代码的位置及版本；必要时本地实现分析的版本和结论 |
| 正例与反例 | 什么会命中；相似模型、文本、路径、字段或历史重现为什么不应命中 |
| 保存与重算 | 需要保存哪些原始字段；派生版本、缓存失效条件及升级验证 |
| 已知边界 | 无法确认的部分、暂缓能力及用户可见行为 |

尽量用原始样本和实现/文档交叉核实；记录证据强度，不能把社区推测写成官方保证。只有样本证据时，应限定到已观测结构并说明边界。源码中的字段名称本身也不证明其语义。

建议覆盖这些样本：首次输入、连续追问、两次相同输入、中断后继续、工具往返、搜索、上下文压缩、预热/后台任务、失败与断连、HTTP/WS、多会话并行及历史消息重现。未碰到的 fork、恢复、多目录等能力可以暂缓，但必须明确，不补推测逻辑。

真实数据仅在授权范围内只读研究；提交的 fixture 使用合成数据，保留协议结构和边界，不复制私人会话或凭据。

## 3. 采集与解析：先保证事实没有被改变

- **采集单位**：明确什么算一条请求。WS 握手、连接级错误、请求帧和多次响应不能混成一个会话请求；HTTP 流式分块也不能每块各计一次。
- **业务透明性**：解析、脱敏、截断、持久化仅处理审计副本。保留真实业务的正文、认证、状态、首段交付和取消语义；审计失败不能重放模型请求或工具调用。
- **保留重算材料**：按现有隐私与保留策略保存请求、响应、相关元数据、协议/schema 和完整性状态。这里的“原文”是应用保留下来的审计内容，不承诺无限量、未脱敏或永不过期。
- **解析结构**：核对 JSON/SSE/WS 封装、文本与思考、工具调用 ID/参数/返回、历史与当前输入、上下文更新、错误对象。工具返回或注入上下文即使 `role=user`，也不能直接视为用户新输入。
- **不完整捕获**：区别业务失败、用户取消、审计截断、正文过期与格式损坏。不得把不完整 JSON 的局部字符串当成完整结构证据。
- **传输标识**：优先使用明确 transport。历史缺失字段只按已验证的旧 schema 与消息特征推导，不统一默认 HTTP，也不把协议族擅自写成 HTTPS/WSS。
- **采集范围**：只有确定为非模型接口，才考虑精确排除。模型调用即使返回 503 或固定错误文本也应保留；错误内容不能证明接口不值得采集。

路径级“不采集”与“不解密”不同：当前 Antigravity 的精确后台接口排除发生在解密之后，只省略审计，业务仍正常转发。新增排除规则必须验证 host、method、原始 path 及相似反例，不能顺手扩大为整个域名绕过 TLS。

参考：[捕获输入](../src/main/attribution/capture.ts)、[协议识别](../src/shared/captureProtocol.ts)、[审计范围](../src/shared/auditScope.ts)、[协议解析](../src/main/schemas/types.ts)。

## 4. 会话：确认唯一身份，避免串线

1. 列出所有会话候选字段，核实各自作用域、格式和语义。相同含义的多个有效字段必须一致；冲突保留候选和原因，不按读取顺序选一个。
2. 会话隔离键包含 Agent。父会话 ID 是关系，不应覆盖子会话自己的身份；共享 workspace/session 字段需要先证明它真的是对话标识。
3. WS 握手头只属于连接。不能未经验证把握手上的会话/轮次元数据沿用到此连接的每一帧。
4. 没有可确认的会话 ID，独立保留请求。不能因为同一时刻、同一提示词、同一模型或同一工具结果，把它塞进最近会话。
5. 原始身份与后续得到的父子关联分开保存；不要改写原始字段来制造归属证据。

当前例子：Antigravity 使用已验证的 `cascade_id` 与结构化 `requestId`；Codex 对 HTTP 单次请求与 WS 当前请求帧分别提取 `thread_id`。具体结构见各自适配器，不能直接移植字段名。

## 5. 轮次：区分原生证据与产品分组

### 原生规则因 Agent 而异

| Agent | 当前规则 | 重要边界 |
| --- | --- | --- |
| Antigravity | 原生日志中 `source=USER_EXPLICIT` **且** `type=USER_INPUT`；请求的明确步骤位置定位到最近的已观测输入 | `step_index` 用于位置与身份，不单独创建轮次；不要求步骤从 0 连续 |
| Codex | 从已核实作用域提取明确 `turn_id` | 相同 ID 不因额外请求而分轮；缺失时不按消息文本或握手旧值猜测 |

不能以文本变化、相同提示词、响应结束、时间间隔、重试、执行 ID 改变、工具调用、CHECKPOINT 或模型切换单独判定新轮次。客户端版本用于证据定位和诊断，不应无理由限制为“最近几个版本”；需要限制的是已验证的协议结构和字段契约。

### 产品分组遵循统一的用户预期

新增 Agent 的方案应明确实现以下行为，并说明原生证据如何驱动它：

- 每个已确认会话从第一个请求起至少有一个轮次；没有捕获到用户输入时，使用默认轮次。
- 只有明确的新轮次证据才切换当前轮次；没有新标志时，后续请求沿用当前轮次。
- 中断、日志缺号或末尾尚未同步，不终止当前轮次，不单独生成会话内的“其他请求”。
- 补到新的明确输入证据后可以重算分组；相同证据和规则版本必须得到相同结果。
- 默认轮次属于产品分组，不代表发现了一个原生用户输入事件；不得伪造 inputIndex、turn_id 或抹掉原生冲突。

当前 Antigravity 与 Codex 通过 `turnGrouping: 'observed_inputs'` 声明该策略，共享投影按稳定的请求顺序维护默认/活跃轮次；有效原生轮次与已确认工具关联仍保留各自归属。这个机制是确定的产品规则，不是猜测缺失日志里发生了什么。Codex 的预热和后台记忆请求只延续产品轮次，独立执行 ID 仍保留在原生决策中；迟到的已知旧轮请求回到原组，不倒退活跃轮次。原生 ID 型 Agent 要在方案中明确如何协调默认轮次与原生 ID，不能直接套用 Antigravity 的步骤结构。详见 [Codex 适配实现](../src/main/attribution/adapters/codex.ts)。

例：默认轮次中的请求 A、B → 捕获明确输入 U1 → C、D → 日志缺号 → E → 明确输入 U2 → F。展示为 `[A,B] / [C,D,E] / [F]`。缺口不制造新轮；如果后来补出缺口中的明确输入，才按新证据重新分组。

这套规则只适用于已确认的会话。会话标识缺失或冲突仍要独立处理，不能用默认轮次跨会话兜底。

参考：[Antigravity 适配器](../src/main/attribution/adapters/antigravity.ts)、[共享判定契约](../src/shared/attribution.ts)、[产品投影](../src/main/attribution/view.ts)。

## 6. 辅助请求、子 Agent 与父子关联

用途、会话身份和父子关系是三个独立结论，允许只确认其中一个。

- 当前标题生成、终端输入检测、网页搜索的用途识别，采用**特定结构位置中的已验证完整系统指令模板**。不能仅匹配“title”“YES/NO”“search”等关键词，不能扫描用户文本，更不能按模型名称选择。
- Codex 的预热、后台记忆任务、上下文压缩采用已核实作用域内的规范 metadata 字段，预热还需 `generate=false` 且原生 turn 缺失。用途和会话身份分别判定，字段冲突不任选一个值。
- 完整模板匹配证明的是当前分类规则命中，不证明请求来自某个主会话，也不证明一定存在独立子 Agent。模板变化须收集新证据、加反例并升级规则，不擅自改成模糊匹配。
- `requestType=checkpoint/chat` 等尚未核实语义的字段，不能作为必要条件过分收窄，也不能作为充分条件扩大判定。
- 优先使用明确父子标识或调用标识。没有显式关联时，只有经过验证、完整且唯一的证据链才能建立关系；语义相似、相邻时间不能替代。
- Antigravity Search 的现有证据链是：实际发起请求的 `search_web` 调用 ID/查询 → 独立搜索响应 → 主会话相同调用的返回；精确核对查询、按已验证规则渲染的完整正文、引用与来源。后续历史再次携带结果，不会把搜索移到新的消费者轮次。
- 多候选、跨会话复制、缺发起请求、响应截断、失败或格式变化时，按既定规则拒绝自动关联。保持用途入口和原始记录，不能丢弃请求或记成零费用。

已确认关联的子请求在对应会话/轮次中展示，保留自己的原文和用量；未关联的辅助请求按用途提供入口。辅助集合是导航视图，不是新的计费记录；与会话按时间混排，不固定沉底。

参考：[用途规则](../src/main/attribution/adapters/antigravityPurpose.ts)、[Search 关联规则实现](../src/main/attribution/adapters/antigravity.ts)。

## 7. 用量、名称与界面语义

**用量只采信协议明确报告的 usage。** 核对字段路径、数值类型、输入/输出/缓存/思考/总量的包含关系，以及流式事件是增量还是累计值。不要把累计 usage 多次相加，也不要把缓存或思考再次叠加到已包含它们的总量。

显式报告的 0 与缺失不同；缺失显示“用量不可用”，不按字符、思考文本、未知数字字段或 Prompt 占比估算 Token。自定义协议映射同样需要明确字段。请求、会话、统计页、账本与导出应保持一致；导航重复引用不重复记账。失败响应有合法 usage 时也不能随意丢弃。

会话名取首个可确认的用户提示词摘要，轮次名取该轮的用户提示词；缺少文本统一“未识别名称”，不加“轮次 N”或会话 ID 前缀。名称不参与身份判断。`role=user` 可能包含上下文和历史，标题提取必须验证它确实属于当前用户输入；图片/工具/空内容不能猜名称。

左侧选择会话和轮次，右侧展示请求；页面不承担规则判定，不展示内部缺失原因与证据清单。需要排查的信息保留在诊断与持久化证据中。Electron IPC 与浏览器 Web 使用同一查询与分组逻辑，不能各实现一套。

参考：[reported usage 约束与契约](../src/shared/attribution.ts)、[会话展示与名称约定](../src/main/attribution/view.ts)。

## 8. 外部证据必须进入本应用

如果依赖源 Agent 的日志或本地数据库：

1. 自动发现已验证的默认位置，尊重用户自定义路径；不存在安装时不创建源目录、不要求用户猜路径。
2. 只读读取，核对路径范围、身份、格式和大小限制；不能仅因同目录或时间相近就合并证据。
3. 在后台采集并保存参与判定的原始记录及必要身份元数据，包含格式、来源和观察时间；未知字段在保留限额内留存，不能只保存解析后的少量结论。
4. 不可变观察与可重算投影分离，按作用域共享、去重并保留冲突；页面查询只读本应用已保存的事实，不现场依赖源日志。
5. 源日志删除、暂不可读或缩短，不否定本应用已经保存的事实；内容改写则保留冲突。不能拼接不相交的片段来伪造完整历史。
6. 测试首次缺失、迟到、更新、删除、重开、正文过期和最后引用清理。首次采集前已丢失的源数据无法凭空恢复；受大小限制的档案也不能宣称完整保留。

源日志的后台重试只重试证据采集，不触发模型调用。原始事实、规则版本、派生身份、产品分组与关联关系必须能区分，避免下一次升级失去重算依据。

参考：[归属仓储与证据持久化](../src/main/attribution/repository.ts)。

## 9. 实现入口与扩展边界

| 层 | 入口 | 新增适配要做什么 |
| --- | --- | --- |
| 采集与协议解析 | `core-go/`、`src/main/parser.ts`、`src/main/schemas/` | 核对 Agent 识别、传输、完整性和解析；尽量复用已有协议，不把归属规则放进代理 |
| 公共 Agent 分类 | `src/shared/agent.ts`、renderer 类型与导航 | 显式核对分类、图标、筛选和统计；新增适配器不会自动生成完整产品入口 |
| 捕获输入 | `src/main/attribution/capture.ts` | 核对所需头是否进入白名单、是否需要响应证据；不带入凭据，不拿旧派生身份反推原文 |
| 适配器 | `src/main/attribution/contracts.ts`、`adapters/<agent>.ts` | `matches` 唯一匹配；`extract` 提取事实；`resolve` 纯计算；稳定 `id` 和规则 `version` |
| 可选原生证据源 | `sources/<agent>.ts`、`registry.ts` | 只读 I/O 与纯规则分离；需要时提供 `decodeEvidence`、`reconcile`，无原生依赖使用 capture 模式 |
| 可选关联规则 | 适配器 `relate` | 从完整候选集合计算关联，覆盖重复历史、缺失与冲突；不在局部批次持久化不完整关系 |
| 编排、存储与后台线程 | `service.ts`、`repository.ts`、`worker.ts`、`workerClient.ts` | 复用版本化投影、观察、待办、事务、缓存与线程生命周期；不新增按 Agent 名分支的业务流水线 |
| 产品展示 | `view.ts`、共享契约、renderer 导航 | 复用明确的分组策略、名称与用途，前端不重新解析协议 |

当前不是动态插件系统：适配器和证据源需显式注册；分类联合类型、捕获头白名单与响应读取也有现存边界。`matches` 要能在当前服务的轻量候选输入下选择适配器，不能假定服务已提前读取完整正文。新需求突破边界时，先定义必要的能力契约，再小范围调整共享入口。

`NativeArchive`、`NativeStep` 和 locator 当前仍含 Antigravity 专用结构。新 Agent 没有这些概念时，显式扩展带类型区分的证据契约，不能把新格式硬塞成假的 trajectory/step。不要为尚不存在的 Agent 引入通用 DSL、动态加载器或巨型配置引擎。

解析、身份、用途、标题、关联等规则变化，均需核对版本与失效范围。依赖响应的规则，响应更新也必须使事实失效；不能只监听请求正文变化。跨记录关系因新增候选、删除或过期而改变时，重算完整关系。

## 10. 性能与历史升级是适配的一部分

- 普通列表使用轻量数据与已保存事实，不逐请求重复读大报文、解压或解析整套日志；SQL 批量查询，循环外准备语句，批量参数数量受控。
- 大报文与归属重算复用后台线程；线程失败要显式失败，不静默退回主线程做全量计算。IPC/Web 复用同一服务结果。
- 缓存必须基于原始输入、规则版本和观察集合的有效性；新证据、响应完成、并发写入、删除与过期均有失效路径。优化不能省去一致性与完整性校验。
- 测量首次重算、重启加载、无变化刷新、新增单条和批量导入，记录数据量、耗时及主线程响应；不能只测热缓存或把后台查询耗时当成端到端页面耗时。
- 升级以新规则重算派生结果，保留原始事实；schema 变化验证事务、重开及失败回滚。回退代码与恢复数据分开设计，不能假定跨版本写库安全。
- 历史数据修复与在线识别分开。真实修复需要明确授权、只读计划、备份、事务、并发校验及幂等性；缺失原文不能猜测修复，也不能借规则升级自动清理历史。

参考：[性能测量与开发规范](DEVELOPMENT.md)。

## 11. 从方案到验收的最小清单

先定义范围，再逐项补测试。以下各项应标记“通过 / 待验证 / 不适用及原因”，不能用一个总测试数替代。

| 验收项 | 至少覆盖 |
| --- | --- |
| 识别与会话 | 唯一适配器、多个匹配冲突、同名提示词跨会话、字段缺失/非法/矛盾、多 Agent 并存 |
| 轮次 | 默认轮次、明确新边界、同文重复输入、连续请求、缺号/中断、迟到证据、无变化重放；原生 ID 型另验 ID 作用域 |
